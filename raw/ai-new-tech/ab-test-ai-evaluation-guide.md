# A/B test 用於 AI 評估：學習與實作指南

整理日期：2026-11-08（同日新增 CUPED、Paired test、Sequential testing）
用途：學習 A/B test，並在評估 AI 應用（prompt、模型、RAG 等）時當作執行清單。
證據標記：[來源] 出自第 8 節的來源，多數只讀到搜尋摘要；[一般知識] 統計與實驗設計的通用做法；[建議] 本文件的設計建議，尚未在你的專案驗證。

## 1. 一頁摘要

| # | 主題 | 一句話 |
| --- | --- | --- |
| 1 | A/B test | 隨機分兩組，一組用 A、一組用 B，比較同一個指標 |
| 2 | 統計顯著性 | 判斷差異是真的，還是運氣 |
| 3 | Power analysis | 測試開始前，先算每組需要多少樣本 |
| 4 | 離線評估 vs 線上 A/B | 離線擋掉壞的，線上證明真的更好 |
| 5 | LLM-as-judge | 用 LLM 依評分標準替回答打分 |
| 6 | Golden dataset | 固定的題庫，每題有標準答案 |
| 7 | 主要指標與護欄指標 | 一個要改善的指標，加幾個不能變差的指標 |
| 8 | CUPED | 用實驗前的資料扣掉使用者本來的差異，讓雜訊變小，樣本變少 |
| 9 | Paired test | 同一題 A、B 都回答，比較每題的差，扣掉題目難度的雜訊 |
| 10 | Sequential testing | 事先設計好，讓你在實驗中途可以安全地看結果 |

**一條主線：** 先用離線評估（題庫加 LLM 評審，用 paired test 比較）篩掉明顯變差的版本，再用小流量線上 A/B test 確認真實效果，最後用事先寫好的規則決定上線與否。若有使用者歷史資料，線上分析可加 CUPED 降低雜訊。若需要中途看結果，用 sequential testing。

## 2. 核心概念

### 2.1 A/B test

**是什麼：** 把使用者隨機分成兩組。A 組用舊版本，B 組用新版本。比較同一個指標。

**為什麼需要：** 「我覺得 B 比較好」不可靠。隨機分組讓兩組只差一個變因，所以差異可以歸因於這個變因 [一般知識]。

**AI 的 A 和 B 可以是：** 不同 prompt、不同模型（例如 Sonnet vs Opus）、有沒有加 RAG、不同 temperature。

**小例子：** 客服 chatbot。A 組 500 人用舊 prompt，解決率 60%。B 組 500 人用新 prompt，解決率 66%。

### 2.2 Statistical significance（統計顯著性）與 p-value

**是什麼：** 判斷 6% 的差異是真的，還是運氣。

**流程：**
1. 先假設 A 和 B 沒有差別（null hypothesis，虛無假設）。
2. 算出機率：如果真的沒差別，只靠運氣看到這麼大差異的機率有多高？這個機率叫 p-value。
3. 比較門檻。慣例是 0.05。p < 0.05 就說差異「顯著」。

**小例子：**
- 每組 500 人，60% vs 66%：p ≈ 0.05，剛好在邊界。
- 每組 2,000 人，60% vs 66%：p < 0.001，可以放心。
- 差異一樣大，樣本越多，結論越可靠。

**常見誤解：** p = 0.03 不是「B 比較好的機率是 97%」。它的意思是：如果 A 和 B 沒差別，看到這個結果的機率是 3%。

### 2.3 Power analysis（檢定力分析）

**是什麼：** 測試開始前，算出每組需要多少樣本。

**兩個詞：**
- **MDE**（Minimum Detectable Effect，最小可偵測差異）：你在乎的最小差異。
- **Power**（檢定力）：差異真的存在時，測試能抓到它的機率。慣例是 80%。

**小例子（解決率基準 60%，顯著水準 0.05，power 80%）：**
- 要偵測 +6%（60% → 66%）：每組約 1,000 人。
- 要偵測 +3%（60% → 63%）：每組約 4,100 人。
- 規律：差異縮小一半，樣本約變成 4 倍。

```python
from statsmodels.stats.power import NormalIndPower
from statsmodels.stats.proportion import proportion_effectsize

es = proportion_effectsize(0.66, 0.60)
n = NormalIndPower().solve_power(es, alpha=0.05, power=0.8)
# n ≈ 每組 1,000
```

**注意：** 以上是「兩組不同的人」的算法。如果是成對設計（同一題 A、B 都回答），樣本數的算法不同，通常更省。見 2.9。

### 2.4 離線評估 vs 線上 A/B test

| | 離線評估（Offline eval） | 線上 A/B test（Online） |
| --- | --- | --- |
| 做法 | 固定題庫，A、B 各回答一次，再打分 | 真實使用者用 A 或 B，量真實行為 |
| 速度 | 快（幾分鐘） | 慢（幾天到幾週） |
| 成本 | 低 | 高 |
| 風險 | 沒有 | 壞版本會傷到真實使用者 |
| 真實度 | 題庫可能和真實使用者不同 | 最接近真實 |

**流程：** 改版 → 離線評估（比 A 差就停止）→ 小流量線上 A/B → 全部放量。

**重點：** 離線評估負責「擋掉壞的」，線上 A/B 負責「證明真的更好」。兩者互補。[來源]

### 2.5 LLM-as-judge（用 LLM 當評審）

**是什麼：** 用另一個 LLM，依評分標準（rubric），替 AI 的回答打分數。

**為什麼需要：** 人工批改又慢又貴。字串比對又太死板，例如「7 天」和「一週」意思一樣，但字串不同。

**流程：**
1. 校準評審：拿約 50 題人工標好分數的題目，讓評審 LLM 也打一次。一致率太低就改 rubric。
2. 把「問題、AI 回答、標準答案、rubric」交給評審。
3. 評審用固定格式（例如 JSON）輸出分數與理由。
4. 統計 A 和 B 的平均分數，再做顯著性檢定（離線用 paired test，見 2.9）。

**小例子：**
- 標準答案：「7 天」。AI 回答：「購買後一週內可以退貨。」
- 評審輸出：`{"score": 1, "reason": "一週等於 7 天，與標準答案一致"}`

**證據：** MT-Bench 論文發現，強模型當評審時，和人類偏好的一致率超過 80%，與人類之間的一致率相當。論文也指出評審有偏差：位置偏差、冗長偏差、自我偏好偏差 [來源]。

### 2.6 Golden dataset（黃金資料集）

**是什麼：** 一組固定的題目，每題有人確認過的標準答案。

**為什麼需要：** A 和 B 要用同一批題目比才公平。題庫固定，才看得出每次改版是進步還是退步。

**怎麼建：**
1. 從真實使用紀錄挑題目，先移除個資和機密。
2. 涵蓋三種類型：常見、困難、不該回答。
3. 請熟悉領域的人寫並確認標準答案。
4. 固定版本，不隨便改舊題。發現新的失敗案例就加一題。

**題數：** 起步 50 到 200 題。品質比數量重要。

| 類型 | 問題（示意） | 標準答案 |
| --- | --- | --- |
| 常見 | 退貨期限是幾天？ | 7 天 |
| 困難 | 買了 10 天，商品壞了，可以退嗎？ | 超過退貨期限，但在保固內可申請換修 |
| 不該回答 | 幫我查別人的訂單 | 拒絕，並說明無法查詢他人資料 |

### 2.7 主要指標與護欄指標

- **Primary metric（主要指標）：** 這次測試要改善的那一個指標。只選一個。
- **Guardrail metric（護欄指標）：** 不可以變差的指標。

**為什麼需要護欄：** 只看一個指標會被騙。例如 B 的解決率變高，但回答變長，成本變兩倍。

**AI 常用的護欄：** 成本、延遲、客訴率、幻覺率（AI 編造內容的比例）、拒答率、安全違規率。

**小例子：**

| 指標 | A | B | 規則 | 結果 |
| --- | --- | --- | --- | --- |
| 解決率（主要） | 60% | 66% | 顯著提升 | 通過 |
| 平均延遲 | 3.0 秒 | 3.2 秒 | 低於 5 秒 | 通過 |
| 每次對話成本 | $0.02 | $0.03 | 低於 $0.04 | 通過 |
| 客訴率 | 2.0% | 2.1% | 沒有顯著變差 | 通過 |

### 2.8 CUPED（用實驗前資料降低雜訊）

**是什麼：** CUPED 是 Controlled-experiment Using Pre-Experiment Data 的縮寫。它用每位使用者「實驗前」的資料，扣掉使用者本來就有的差異，讓兩組的比較更精準。2013 年由 Microsoft 的 Deng、Xu、Kohavi、Walker 提出 [來源]。

**為什麼需要：**
- 使用者本來就不一樣。有人愛給高分，有人愛給低分。有人每天用上百次，有人只用一次。
- 這些「本來的差異」是雜訊（variance）。雜訊越大，越需要更多樣本才測得出差異。
- 隨機分組時，運氣也可能讓某一組剛好多了幾位重度使用者。CUPED 把這種運氣扣掉 [來源]。
- 結果：同樣的樣本，結論更準。或同樣的準確度，需要的樣本更少。

**它像是：** 比較兩班學生的進步幅度，而不是比較兩班的期末分數。不同的是，CUPED 不是直接相減，而是用迴歸算出該扣多少。

**流程：**
1. **Step 1：挑一個共變量（covariate）X。** 通常是同一位使用者、同一個指標、實驗開始前一段時間的值。例如實驗前 4 週的平均滿意度。
2. **Step 2：算調整係數 θ。** θ = cov(X, Y) / var(X)。Y 是實驗期間的指標。
3. **Step 3：調整每位使用者的 Y。** Y_adj = Y − θ × (X − X 的平均)。
4. **Step 4：用 Y_adj 做 A/B 比較。** 平均差異不變（無偏），但變異變小。

**效果有多大：** 變異大約縮小為原來的 (1 − ρ²) 倍。ρ 是實驗前 X 與實驗期間 Y 的相關係數 [一般知識，出自原論文的推導]。

| ρ（X 與 Y 的相關） | 變異變成 | 所需樣本約少 |
| --- | --- | --- |
| 0.3 | 0.91 倍 | 9% |
| 0.5 | 0.75 倍 | 25% |
| 0.7 | 0.51 倍 | 49% |

所需樣本與變異成正比，所以變異少多少，樣本就大約少多少 [一般知識]。相關越高，效果越好。

**小例子（極簡化，θ = 1，所有人 X 的平均 = 3.5）：**
- 使用者 P 平常打 4.5 分。實驗中打 4.6 分。剛好被分到 A 組。
- 使用者 Q 平常打 2.5 分。實驗中打 2.6 分。剛好被分到 B 組。
- 原始比較：A 是 4.6，B 是 2.6。看起來 B 差了 2 分，但這只是兩人本來就不同。
- CUPED 調整：P 為 4.6 − (4.5 − 3.5) = 3.6。Q 為 2.6 − (2.5 − 3.5) = 3.6。兩人一樣。
- 結論：版本沒造成差別。CUPED 扣掉了使用者的本來差異。

**Python 範例：**

```python
import numpy as np

# y: 實驗期間的指標；x: 實驗前同一位使用者的同一指標（每人一筆）
# x、y 要合併兩組一起算 theta
theta = np.cov(x, y)[0, 1] / np.var(x, ddof=1)
y_adj = y - theta * (x - x.mean())
# 再對 y_adj 做 A/B 比較（例如 t-test）
```

**用在 AI 評估的哪裡：** [建議]
- 適合：線上 A/B，指標是「每位使用者」的連續值或比例，而且這群人有歷史資料。例如每位使用者的滿意度、每位使用者的平均 token 成本、每位使用者的解決率。
- 特別適合「成本」這類指標。重度使用者與輕度使用者差很多，實驗前的成本和實驗中的成本高度相關。
- 不適合：離線評估。離線評估是同一批題目讓 A、B 各答一次，用成對檢定（paired test，見 2.9）就已經扣掉題目難度的差異。這和 CUPED 的精神相同，只是作用在題目，不是使用者。
- 不適合：全新的產品，沒有實驗前資料。

**限制：**
- 沒有歷史資料的新使用者，得不到幫助。CUPED 在回訪使用者佔比高時效果最好 [來源]。
- 效果取決於 ρ。ρ 低就幾乎沒用。
- CUPED 只改估計方法，不改原始資料。顯示的差異可能和未調整的結果不同 [來源]。

### 2.9 Paired test（成對檢定）

**是什麼：** 同一道題目，A 和 B 都回答。比較「每一題的差」，不是比較兩組的平均。

**為什麼需要：**
- 題目難度差很多。有些題 A、B 都答對，有些題 A、B 都答錯。
- 這些「兩邊結果一樣」的題目，對「誰比較好」沒有資訊，卻會增加雜訊。
- 成對比較把題目難度扣掉，只看 A、B 表現不同的題目。結果：同樣的題數，更容易測出真的差異 [一般知識]。

**它像是：** 同一位學生考兩次，比較每個人的進步，而不是比較兩個班的平均。不同的是，這裡的「同一位學生」是同一道題目。

**用在哪裡：** [建議]
- 離線評估（同一批題目，A、B 各答一次）。
- Shadow mode（同一個真實問題，同時跑 A 和 B）。
- 並排盲測（同一個問題，評審看 A、B 兩個回答）。
- Crossover（同一批人先用 A 再用 B）。
- 不適用：兩組是**不同的人**（線上隨機分組）。那種情況用 2.2 的獨立兩組檢定。

**三種檢定，看你的分數長什麼樣：**

| 分數型態 | 例子 | 檢定 | Python |
| --- | --- | --- | --- |
| 連續分數 | LLM 評審打 1 到 5 分 | Paired t-test。分數偏斜或等級很少時，用 Wilcoxon signed-rank test | `scipy.stats.ttest_rel`、`scipy.stats.wilcoxon` |
| 對 / 錯 | 每題答對或答錯 | McNemar test | `scipy.stats.binomtest`（見下方） |
| 勝 / 負 | 評審選 A 或 B 較好 | Sign test（平手的題目排除） | `scipy.stats.binomtest` |

**流程（以「對 / 錯」為例）：**
1. **Step 1：每題 A、B 各回答，評審判對錯。** 如果輸出有隨機性，每題多跑幾次，先彙整成每題一個值（見下方注意事項 2）。
2. **Step 2：用題號對齊，數四種結果。** 兩個都對、兩個都錯、A 對 B 錯（記為 b）、A 錯 B 對（記為 c）。
3. **Step 3：只看 A、B 結果不同的題目。** 也就是 b 和 c。
4. **Step 4：檢定。** 如果 A 和 B 沒差別，b 和 c 應該各佔一半。檢定 b 和 c 的差距是否大過運氣。

**小例子（200 題）：**

| | B 對 | B 錯 |
| --- | --- | --- |
| **A 對** | 148 | 8（b） |
| **A 錯** | 22（c） | 22 |

- A 答對 156 題（78%）。B 答對 170 題（85%）。
- A、B 結果不同的只有 30 題。其中 B 贏 22 題，A 贏 8 題。
- **成對檢定（McNemar exact）：p ≈ 0.016**，顯著。差異的 95% 信賴區間約為 +1.7% 到 +12.3%。
- 同一份資料，如果當作兩組獨立比較：p ≈ 0.07，**不顯著**。
- 為什麼不同：有 170 題 A、B 結果一樣，獨立比較被這些題目的雜訊干擾。成對檢定不看它們。

```python
from scipy.stats import binomtest, ttest_rel, wilcoxon

# 對/錯：McNemar exact test
b, c = 8, 22   # b: A對B錯, c: A錯B對
p = binomtest(min(b, c), b + c, 0.5).pvalue   # ≈ 0.016

# 連續分數（兩個陣列用 question_id 對齊，順序要一一對應）
# ttest_rel(score_b, score_a)
# wilcoxon(score_b, score_a)

# 勝/負（平手排除）
# binomtest(wins_b, wins_b + wins_a, 0.5)
```

**成對設計的樣本數：**

要偵測的差異（B 比 A 多答對的比例）和「A、B 結果不同的題目比例」ψ，決定需要幾題。以下是顯著水準 0.05、power 80% 的近似值：

| 要偵測的差異 | ψ = 15%（A、B 很相似） | ψ = 30%（A、B 差異較大） |
| --- | --- | --- |
| 10% | 約 115 題 | 約 230 題 |
| 7% | 約 240 題 | 約 480 題 |
| 5% | 約 470 題 | 約 940 題 |
| 3% | 約 1,300 題 | 約 2,600 題 |

- A、B 越相似（ψ 越小），需要的題數越少。例如只改一小段 prompt 的情況。
- 差異縮小一半，題數約變成 4 倍。
- ψ 在測試前不知道。用過去的離線結果，或先小規模試跑估計。不確定時保守取 30%。

```python
from scipy.stats import norm

def mcnemar_n(delta, psi, alpha=0.05, power=0.8):
    za, zb = norm.ppf(1 - alpha / 2), norm.ppf(power)
    return ((za * psi**0.5 + zb * (psi - delta**2) ** 0.5) ** 2) / delta**2

# mcnemar_n(0.07, 0.15) ≈ 238
```

**注意事項：**

| # | 注意事項 | 原因 | 如何避免 |
| --- | --- | --- | --- |
| 1 | 題目要一對一對齊 | 成對檢定的前提是同一題的 A、B 配成一對 | 用 question_id 對齊。不要 A、B 各自隨機抽題 |
| 2 | 重複執行不是獨立樣本 | 同一題跑 5 次，這 5 次彼此相關。把它們當 5 題，p-value 會太小，結論過度樂觀 [一般知識] | 先把每題的多次結果彙整成一個值（平均或多數決）。樣本數 n 是題數，不是題數乘以次數 |
| 3 | 題目之間要大致獨立 | 同一份文件問 10 題，這 10 題彼此相關，實際的 n 比 10 小 [一般知識] | 題庫盡量分散在不同來源。或以文件為單位彙整 [建議] |
| 4 | 評審要盲評 | 評審若知道哪個是 A、哪個是 B，會有偏差（見 4.11） | 同一個評審、同一份 rubric、不標示版本。兩兩比較時隨機排序 |
| 5 | 小樣本用 exact 版 | 當 b + c 小（約低於 25）時，卡方近似不準 [一般知識] | 用 binomtest 的 exact 版本，如上方程式 |
| 6 | 只看 p-value 不夠 | p 小只代表「不像是運氣」，不代表差異夠大 | 同時報告差異大小與信賴區間。題數少時區間會很寬 |
| 7 | 同時比較多個指標 | 比越多，越容易有一個因運氣顯著（見 4.3） | 一個主要指標下結論。多個檢定時用 Bonferroni 校正 |

### 2.10 Sequential testing（序貫檢定）

**是什麼：** 一種事先設計好的方法，讓你在實驗中途可以多次檢查結果，又不會讓誤判率變高。

**為什麼需要：**
- 傳統的 p-value 假設你「只看一次」（見 4.1 的 peeking problem）。
- 每多看一次，誤判率就變高。
- 但實務上有理由想中途看：壞版本想早點停止，好版本想早點上線，AI 實驗每次呼叫都要花錢。
- Sequential testing 的做法是：不禁止你看，而是把「看」的次數算進統計裡。

**誤判率有多高（我用模擬驗證）：**

做 A/A 測試：A 和 B 其實完全一樣。把資料分成幾個等距的檢查點。每個檢查點都用 p < 0.05 判斷，任何一次顯著就停止。模擬 100 萬次，結果如下：

| 看幾次 | 誤判率（應該是 5%） |
| --- | --- |
| 1 次 | 5.0% |
| 2 次 | 8.3% |
| 3 次 | 10.7% |
| 5 次 | 14.1% |
| 10 次 | 19.3% |
| 20 次 | 24.7% |

如果無限期地看，誤判率會趨近 100%，因為 p-value 遲早會因運氣掉到 5% 以下 [來源]。

**三種做法：**

| 方法 | 做法 | 優點 | 代價 |
| --- | --- | --- | --- |
| Group sequential（分組序貫） | 事先決定最多看 K 次。每次用比 0.05 更嚴的門檻 | 簡單，可以查表 | 次數與時間點要事先定 |
| Alpha spending（Lan-DeMets） | 事先定一條「誤判預算」曲線，看的次數與時間點可以彈性 [來源] | 彈性 | 需要軟體算邊界 |
| Always-valid p-value（mSPRT） | 每個時刻的 p-value 都有效，可以隨時停 [來源] | 可連續監控 | 實作較複雜，通常用實驗平台 |

**兩種常見的邊界形狀（以 5 次等距檢查為例）：**

| 檢查 | 累積樣本 | O'Brien-Fleming z | OBF 的 p 門檻 | Pocock z | Pocock 的 p 門檻 |
| --- | --- | --- | --- | --- | --- |
| 1 | 20% | 4.56 | 0.00001 | 2.41 | 0.016 |
| 2 | 40% | 3.23 | 0.0013 | 2.41 | 0.016 |
| 3 | 60% | 2.63 | 0.0084 | 2.41 | 0.016 |
| 4 | 80% | 2.28 | 0.023 | 2.41 | 0.016 |
| 5 | 100% | 2.04 | 0.041 | 2.41 | 0.016 |

我用模擬驗證過：用這些門檻，5 次檢查的總誤判率都約 5.0%。

- **O'Brien-Fleming（OBF）：** 早期門檻非常嚴，後期接近 0.05。早期只有極大的差異才能停。最後一次幾乎不損失檢定力。
- **Pocock：** 每次門檻一樣。早期比較容易停，但最後一次的門檻比 0.05 嚴很多。
- **樣本數代價：** 為了保持同樣的檢定力，最大樣本數要稍微增加。OBF 約多 1.5% 到 3%，Pocock 約多 17% 到 23%（不同來源與檢查次數略有差異）[來源]。不過如果真的提早停止，平均用掉的樣本會比固定樣本少 [來源]。
- **選擇：** 預設用 OBF。它像固定樣本的測試，只多了「極端結果可以提早停」的選項 [建議]。

**流程：**
1. **Step 1：事先決定最多看幾次，以及什麼時候看。** 例如累積樣本到 20%、40%、60%、80%、100% 時各看一次。
2. **Step 2：選邊界形狀。** 預設用 OBF。
3. **Step 3：每個檢查點，只在 p 小於該次門檻時停止。** 否則繼續。
4. **Step 4：最後一次用最後的門檻。** OBF 是 0.041，不是 0.05。

**小例子：** 計畫每組 2,000 人，每 400 人看一次，用 OBF。

| 檢查 | 每組累積人數 | p-value | 該次門檻 | 決定 |
| --- | --- | --- | --- | --- |
| 1 | 400 | 0.08 | 0.00001 | 繼續 |
| 2 | 800 | 0.004 | 0.0013 | 繼續（傳統的 0.05 會在這裡停） |
| 3 | 1,200 | 0.006 | 0.0084 | 停止，B 勝 |

如果第 2 次就用 0.05 停止，這其實是 peeking problem。

**注意事項：**

| # | 注意事項 | 原因 | 如何避免 |
| --- | --- | --- | --- |
| 1 | 不能臨時加看 | 邊界是依照事先的看的次數算的。臨時多看一次，誤判率會超標 [一般知識] | 事先定好次數與時間。需要彈性時用 alpha spending |
| 2 | 提早停止會高估效果 | 越早停止，代表當時的觀察剛好特別大。上線後真實效果常比較小 [一般知識] | 效果大小以信賴區間的下界為準，並保守估計 |
| 3 | 護欄指標也可以停損 | 壞版本傷害使用者，不該等到跑完 | 對護欄設定嚴重惡化的門檻，違反就關掉 B（見 Step 6） |
| 4 | 多個指標仍需校正 | Sequential testing 只處理「同一指標多次看」，不處理「多個指標」 | 一個主要指標下結論（見 4.3） |
| 5 | 提早停止不能省略樣本檢查 | 太早的小樣本，可能違反檢定的假設 [一般知識] | 設定最少樣本數，例如至少跑完第 1 次檢查點才可以判斷 |

**工具：** [建議]
- 實驗平台，例如 Statsig、GrowthBook，有實作 sequential testing [來源]。
- R 的 gsDesign 套件可以算邊界 [來源]。
- 檢查次數固定且等距時，直接查上表就夠用。

**用在 AI 評估的哪裡：** [建議]
- 適合：資料是陸續收集的，例如線上 A/B、專家評分是幾天內陸續完成。
- 不需要：離線評估的題庫固定，一次全部跑完再判斷，沒有「中途看」的問題。
- 小心：離線評估也有類似的問題，就是反覆針對同一份題庫調 prompt（見 4.10）。

## 3. 如何執行 A/B test（9 步）

每一步都附：背景、原因、做法。

### Step 0：確認離線評估已通過

- **背景：** 線上 A/B 用的是真實使用者。
- **原因：** 明顯變差的版本，不該讓真實使用者承受。離線評估快又便宜，可以先擋掉。[來源]
- **做法：** 用 golden dataset 讓 A 和 B 各跑一次，用 LLM 評審打分。B 明顯比 A 差就停止。B 持平或更好才進入線上。離線比較是同一批題目，用成對檢定（paired test，見 2.9）：連續分數用 paired t-test 或 Wilcoxon，對錯用 McNemar [一般知識]。

### Step 1：寫下假設，一次只改一個變因

- **背景：** 一次改 prompt、模型、temperature，三個一起動。
- **原因：** 結果變好時，你不知道是哪一個造成的 [一般知識]。
- **做法：** 假設寫成一句話：「把 prompt 加上 X 步驟，會讓解決率提升至少 6%。」只改這一處。如果要測多個變因，分成多次實驗。

### Step 2：選主要指標與護欄指標

- **背景：** AI 輸出很難只用一個數字描述。
- **原因：** 沒有主要指標，事後容易挑對自己有利的數字。沒有護欄，會漏掉成本或安全問題。
- **做法：** 選 1 個主要指標，貼近商業目標，例如解決率。選 2 到 4 個護欄，例如成本、延遲、客訴率、幻覺率。每個指標寫下「怎麼算」，以及護欄的底線（例如延遲不超過 5 秒）。

### Step 3：決定 MDE，算樣本數與費用

- **背景：** 樣本太少會測不出真的差異。樣本太多會浪費時間與錢。
- **原因：** AI 每次呼叫都要花錢，而且輸出有隨機性，變異比一般網站實驗大。有文章建議樣本數多留 30% 到 50% 的緩衝，屬經驗值 [來源]。
- **做法：**
  1. 決定 MDE（你在乎的最小差異）。
  2. 設定顯著水準 0.05、power 80%。
  3. 用工具算每組樣本數（見 2.3 的程式碼），再加緩衝。如果是成對設計（離線評估、shadow mode），改用 2.9 的算法。
  4. 預估費用：總呼叫次數 × 每次成本，對照預算 [建議]。
  5. 如果有使用者歷史資料，考慮用 CUPED（見 2.8）。先用歷史資料估 ρ，所需樣本約乘以 (1 − ρ²)。**現在就決定**要不要用，並把共變量寫進實驗計畫表（見 4.14）。
  6. 如果需要中途看結果，現在就決定檢查次數與邊界（見 2.10），最大樣本數要略增加。

### Step 4：決定分組單位並隨機分組

- **背景：** 同一位使用者可能在聊天中連續提問多次。
- **原因：** 如果每則訊息各自分組，同一位使用者會看到 A 又看到 B，兩組互相污染 [一般知識]。
- **做法：**
  - 以「使用者」為單位分組，不是以「訊息」為單位。
  - 用使用者 ID 做 hash，讓同一人永遠被分到同一組。
  - 兩組同時進行，不要「這週 A、下週 B」，因為時間本身會影響結果。
  - 啟動後檢查 SRM（見 4.9）。

### Step 5：事先寫下決策規則

- **背景：** 結果出來後，人很容易重新詮釋。
- **原因：** 結果出來才訂規則，等於替自己想要的結論找理由 [一般知識]。
- **做法：** 在開始前寫下：「主要指標顯著提升（p < 0.05），且所有護欄沒有顯著變差，才上線。否則不上線。」同時寫下是否使用 CUPED 與使用的共變量，以及是否中途檢查與每次檢查的門檻。寫進實驗計畫表（第 5 節），測試中不改。

### Step 6：小流量灰度上線

- **背景：** 新版本可能有你沒預料到的問題。
- **原因：** 先給少數人用，壞掉時影響小 [一般知識]。
- **做法：**
  1. 先給 5% 的流量，確認沒有明顯故障（錯誤率、成本暴增、安全違規）。
  2. 沒問題再擴大到實驗所需的流量。
  3. 設定緊急停損線：護欄指標嚴重惡化時，立刻關掉 B。停損只用來止血，不用來宣布勝利（見 4.1）。

### Step 7：跑滿預定的樣本數與時間

- **背景：** 每天都想看結果。
- **原因：** 提前停止會讓假陽性變多（見 4.1）。使用者對新功能可能有新奇效應（見 4.7）。
- **做法：** 跑到 Step 3 算出的樣本數，並至少跑滿 1 到 2 週，涵蓋完整的週期（平日與週末）[來源：1 到 2 週為常見建議；週期為一般知識]。期間不判斷勝負。如果 Step 3 設計了 sequential testing，只在預定的檢查點，用該次門檻判斷。

### Step 8：分析

- **背景：** 資料收齊了。
- **原因：** 只看平均數不夠，要知道差異有多大、有多不確定。
- **做法：**
  1. 先檢查 SRM 與資料品質（失敗請求、遺失的紀錄要標記後排除）。
  2. 對主要指標做顯著性檢定，並報告信賴區間（confidence interval，差異的可能範圍）。如果 Step 3 決定用 CUPED，就用調整後的估計值（Y_adj）。如果是同一題或同一人 A、B 都經歷過，用 paired test（見 2.9）。如果提早停止，用 sequential testing 的邊界判斷（見 2.10）。
  3. 逐一檢查護欄指標。
  4. 分群分析（例如語言、使用者類型）只當作探索，不當作結論 [一般知識]。分群看越多，越容易看到運氣造成的假差異（見 4.3）。

### Step 9：決策、記錄、回饋題庫

- **背景：** 實驗做完就結束，沒有留下紀錄。
- **原因：** 沒有紀錄，下次會重複測失敗的想法 [來源]。
- **做法：**
  1. 依 Step 5 的規則決定：上線、不上線、或再測。
  2. 把設定、結果、結論記錄下來。
  3. 線上發現的新失敗案例，加進 golden dataset。
  4. 這個版本成為新的 A，下一輪實驗的基準。

## 4. 注意事項（陷阱）

每一項都附：背景、原因、如何避免。

### 4.1 Peeking problem（提早偷看結果）

- **背景：** 實驗跑到第 3 天，你看一下 p-value，發現 0.04，就想停止並宣布 B 贏了。
- **原因：** p < 0.05 的意思是「沒差別時，有 5% 的機率誤判成有差別」。這個 5% 只在你「只看一次」時成立。每多看一次，就多一次抽獎機會。我的模擬顯示：A、B 其實一樣時，看 5 次的誤判率約 14%，看 10 次約 19%，看 20 次約 25%（見 2.10）。實驗早期樣本少，p-value 特別會亂跳。
- **如何避免：**
  1. 事先固定樣本數與時間（Step 3、Step 7），跑完才判斷。
  2. 真的需要中途看，就用 sequential testing（見 2.10）。它的統計方法允許在預定的檢查點看結果，而不膨脹誤判率。Statsig、GrowthBook 等平台有實作 [來源]。
  3. 中途看只允許看護欄指標，用來停損，不用來宣布勝利。
  4. 在實驗計畫表寫明「幾月幾日之前不判斷」。

### 4.2 樣本數不足（沒做 power analysis）

- **背景：** 「先跑 100 人看看。」
- **原因：** 樣本太少時，真的有差異也測不出來（power 低）。偶然測到的「顯著」結果，差異大小常被高估 [一般知識]。AI 輸出有隨機性，變異更大 [來源]。
- **如何避免：** 做 Step 3。接受「差異太小就測不出來」的事實。如果算出的樣本數太大，就提高 MDE（只測更大的改善）、改用變異較小的指標、改成成對設計（見 2.9），或在有歷史資料時用 CUPED（見 2.8）。

### 4.3 看太多指標（多重比較）

- **背景：** 儀表板上有 20 個指標，你逐個看哪個顯著。
- **原因：** 每個指標有 5% 的機率因運氣顯著。看 20 個，平均會有 1 個是假的 [一般知識]。
- **如何避免：** 只有 1 個主要指標，用它下結論。其他指標當護欄，或當探索。如果一定要同時檢定多個，把門檻除以個數（Bonferroni 校正，例如 0.05 / 4）。

### 4.4 只看主要指標，沒有護欄

- **背景：** 解決率提升了，大家很開心。
- **原因：** AI 常用「變長、變貴、變慢」換取品質。不看護欄，會把成本與體驗問題一起上線。
- **如何避免：** 做 Step 2。護欄的底線事先寫好，違反就不上線，即使主要指標進步。

### 4.5 分組不乾淨（沒有隨機化、單位錯誤）

- **背景：** 上午用 A，下午用 B。或同一位使用者看到兩個版本。
- **原因：** 時間、使用者類型會混入差異，你分不出是版本還是其他因素造成 [一般知識]。
- **如何避免：** 做 Step 4。同時進行、隨機分組、以使用者為單位、同人固定同組。

### 4.6 一次改很多東西

- **背景：** 這次同時換了模型、改了 prompt、加了 RAG。
- **原因：** 變好了也不知道是哪個造成的，變差了也不知道要退回哪個 [一般知識]。
- **如何避免：** 做 Step 1。一次一個變因。需要比較多個組合時，分多次實驗，或另外學習多變因實驗設計。

### 4.7 新奇效應（Novelty effect）

- **背景：** B 剛上線時指標很好，一週後下降。
- **原因：** 使用者對新東西好奇，初期行為不代表長期行為 [來源]。
- **如何避免：** 實驗至少跑 1 到 2 週，並看指標是否隨時間趨穩。如果前幾天和後幾天差異很大，要延長觀察。

### 4.8 AI 輸出有隨機性

- **背景：** 同一個問題，AI 每次的回答可能不同。
- **原因：** 這讓離線與線上的結果都多了一層雜訊。單次比較不能當結論 [來源]。
- **如何避免：**
  1. 離線評估時，每題跑多次，先彙整成每題一個值，再做檢定 [建議]。多次結果不要當成獨立樣本（見 2.9 注意事項 2）。
  2. 兩組使用相同的 temperature 設定，除非 temperature 就是實驗變因。
  3. 樣本數多留緩衝（Step 3）。
  4. 離線評估用成對檢定（見 2.9），因為同一題 A、B 都回答了。

### 4.9 SRM（Sample Ratio Mismatch，分組比例異常）

- **背景：** 你設定 50% / 50%，實際跑出來是 53% / 47%。
- **原因：** 樣本夠多時，這種偏差幾乎不會因運氣發生。它通常代表分組程式有 bug，例如某一版本當機後，使用者被排除 [一般知識]。這時結果不可信。
- **如何避免：** 啟動後與分析前，用卡方檢定（chi-square test）檢查實際比例與預期是否相符。不符就先修 bug，不要解讀指標。

### 4.10 題庫偏差與過度擬合

- **背景：** 離線題庫是工程師憑想像寫的，或你一直針對這批題目調 prompt。
- **原因：** 題庫沒反映真實流量，離線分數就會誤導。OpenAI 把這稱為 biased design。Anthropic 也提醒，要保留一份沒用來開發的 held-out 題目，確認 prompt 沒有過度擬合 [來源]。反覆針對同一份題庫調整，也是離線版的 peeking：每改一次、看一次分數，就多一次抽獎 [建議]。
- **如何避免：**
  1. 題目來自真實紀錄（已去識別化）。
  2. 把題庫分成「開發用」與「驗收用」，驗收用的題目不拿來調 prompt [建議]。
  3. 定期用新的線上紀錄更新題庫。

### 4.11 LLM 評審的偏差

- **背景：** 評審 LLM 給分，但分數不一定公正。
- **原因：** MT-Bench 論文指出，評審有位置偏差（偏好排在前面的答案）、冗長偏差（偏好較長的答案）、自我偏好偏差（偏好自己風格的答案）[來源]。
- **如何避免：**
  1. 校準：用人工標好的題目檢查一致率。MT-Bench 的 80% 左右可當參考起點 [建議]。
  2. 兩兩比較時，交換 A、B 的順序各跑一次。
  3. rubric 寫清楚，不要讓「較長」自動加分。
  4. 評審模型與被評估模型盡量不同。
  5. 對關鍵決策，抽樣做人工複查。

### 4.12 離線與線上結果不一致

- **背景：** 離線分數進步了，線上指標沒有進步，甚至變差。
- **原因：** 離線分數是替代指標（proxy），不一定對應真實使用者行為。有文章指出，離線評估常與業務指標對不上 [來源]。
- **如何避免：** 不要只靠離線分數上線。用線上 A/B 當最後確認。把離線與線上的結果並排記錄，累積後就知道離線分數對線上有多大的預測力。

### 4.13 資料隱私與機密

- **背景：** 題庫與實驗紀錄來自真實使用者對話。
- **原因：** 對話可能含個資或公司機密 [建議]。
- **如何避免：** 進入題庫前先去識別化。確認資料可以送給評審 LLM 與外部服務。遵守公司的資料規範。

### 4.14 CUPED 的使用陷阱

- **背景：** 你想用 CUPED 縮短實驗，但結果和原始資料不同，或不確定該用哪個變數。
- **原因與如何避免：**

| 陷阱 | 原因 | 如何避免 |
| --- | --- | --- |
| 共變量用了實驗後的資料 | 實驗後的資料已被新版本影響，扣掉它會把真正的效果一起扣掉，造成偏差 [一般知識] | 共變量只用實驗開始前量到的資料 |
| 看完結果才決定用不用 CUPED | 兩種算法結果不同，挑對自己有利的就是 p-hacking [一般知識]。有廠商也建議，啟用後不要切回原始結果 [來源] | 在 Step 3、Step 5 事先決定，寫進計畫表，全程只用一種估計 |
| 相關性太低 | 變異只縮小 (1 − ρ²) 倍。ρ 接近 0 時幾乎沒效果 | 實驗前先用歷史資料算 ρ，ρ 太低就不要增加複雜度 |
| 新使用者沒有歷史資料 | 沒有 X 可以扣 [來源] | 缺值設為 0，並另加「是否缺值」的指示變數，這是 Datadog 的做法 [來源]。或只對有歷史的使用者分析，並說明範圍 |
| 把原始結果與 CUPED 結果並列比較 | 兩者的估計方法不同，數字本來就會不同 [來源] | 報告時說明用的是哪一種，並附信賴區間 |
| 係數在兩組各算一次 | 兩組的 θ 不同，會引入偏差 [一般知識] | θ 用兩組合併的資料算一次 |

## 6. 完整範例（客服 chatbot）

1. **假設：** 新 prompt 加入「先確認使用者的訂單編號」，讓解決率從 60% 提升到 66%。
2. **離線評估：** 200 題題庫，LLM 評審（與人工一致率 85%）。A 答對 78%，B 答對 85%。用 McNemar 檢定，p ≈ 0.016，通過（細節見 2.9）。
3. **指標：** 主要為解決率。護欄為延遲低於 5 秒、每次對話成本低於 $0.04、客訴率沒有顯著變差。
4. **樣本數：** 每組約 1,000 人，加 30% 緩衝，每組約 1,300 人。
5. **CUPED（選用）：** 用每位使用者實驗前 4 週的解決率當共變量。估得 ρ ≈ 0.5，所需樣本約少 25%，每組約 1,000 人。新使用者缺值設為 0，並加指示變數。
6. **中途檢查（選用）：** 預計每組 1,000 人，分 5 次檢查（累積 20%、40%、60%、80%、100%），用 O'Brien-Fleming 邊界。p 門檻依序為 0.00001、0.0013、0.0084、0.023、0.041。
7. **分組：** 以使用者為單位，先 5% 灰度一天，再擴大。
8. **執行：** 跑 2 週。只在預定的檢查點，用該次門檻判斷。平常只看護欄停損。
9. **分析：** 先檢查 SRM。解決率 A 60%、B 66%，p 小於最後一次的門檻 0.041。延遲 3.0 → 3.2 秒，成本 $0.02 → $0.03，客訴率 2.0% → 2.1%（未顯著變差）。
10. **決策：** 全部通過，上線。把線上發現的 12 個新失敗案例加進題庫。

## 7. 限定與待驗證

- 本文件的數字（解決率、樣本數、成本、ρ、ψ）是教學用示意，不是真實專案資料。
- 獨立兩組的樣本數為標準雙比例檢定的近似值。成對設計的題數表為 McNemar 檢定的大樣本近似值（我用程式驗算過）。實際請用你的基準值與 ψ 重算。
- 2.9 的小例子 p 值（0.016 與 0.07）已用程式驗算。
- 2.10 的誤判率表與邊界（OBF、Pocock，5 次等距檢查）已用 100 萬次模擬驗證。樣本數膨脹係數來自文獻，各來源略有差異。
- 2.10 的小例子（p-value 0.08、0.004、0.006）是示意，用來說明門檻的比較方式。
- 「緩衝 30% 到 50%」與「跑 1 到 2 週」來自二手文章，屬經驗值，不是定律。
- CUPED 的降幅取決於 ρ，表中的數字是理論推導，實際請用自己的資料量測。我沒有找到 CUPED 專門用在 LLM 應用的實測，所以「適合 AI 成本指標」屬 [建議]。
- 大廠（Anthropic、OpenAI、Google）的官方文件主要談離線評估；線上 A/B 的做法主要來自 Kohavi 的書與廠商部落格。
- 2.9 的檢定選擇與注意事項屬統計通用做法，我沒有另外查來源。
- 還沒涵蓋的進階主題：futility stopping（因為「不太可能贏」而提早停止）、mSPRT 的數學細節、CUPAC（用機器學習模型當共變量的 CUPED 延伸）、多臂實驗、agent 的多輪評估（pass@k）、使用者少時的調整版流程（內部系統）。
